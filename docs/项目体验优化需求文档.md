# 项目体验优化需求文档

版本：1.0；日期：2026-11-19；状态：需求与执行方案已建立，优化和实测结果按阶段另行登记。

配套文件：[项目体验优化验收标准](项目体验优化验收标准.md)。本次范围由用户提出：美术、性能、网络、联机、语音清晰度、流畅度和 UI 按钮布局优化；不得改变游戏规则和业务逻辑。

2026-11-20 布局更新以 [牌桌布局规范](牌桌布局规范.md) 为准，记录用户实际试玩后的逐项要求及覆盖的旧设计。参数、测试场景与用户确认事项分别登记。

## 1. 项目与基线

- 目标平台：安卓手机、横屏。先在两台安卓模拟器复现，再用真实安卓设备确认触摸、声音和持续性能；模拟器不能代替真机结论。
- 有效代码源：`build/wall-layout`，提交 `6e0937ecb4b64fe208ff03f56ea568514537c8d0`，项目版本标识为 1.6.30，Godot 4.7、GL Compatibility。
- 独立实施目录：`build/quality-optimization`；分支：`codex/quality-optimization`。不修改项目根目录的历史工作，也不覆盖原工作区。
- 基线还包含原工作区 7 个未提交文件，涉及上一轮结算得分项展示及其测试、文档。这些成果已按原字节复制，属于继承基线，不算本轮新增优化。
- 来源、文件摘要和原修改补丁存于独立工作区的 `build/quality-optimization-evidence/`。正式测量必须记录精确版本、改动、设备和配置，不能只写“1.6.30”。
- 已有测试脚本不等于本轮已通过；历史截图、历史性能报告不作为当前版本通过的证据。

## 2. 最高约束：规则与业务逻辑冻结（RULE-01）

以下均保持当前基线，包括当前实现中的边界行为：

1. 牌组、洗牌随机性、固定牌墙数组、牌头牌尾定义、庄家与座次、开墙和发牌顺序。
2. 普通摸牌、杠后补牌、翻鸡来源和耗尽处理；牌的唯一身份、所有权和数量。
3. 出牌、碰、明杠、暗杠、补杠、抢杠、胡牌、响应优先级和合法操作集合。
4. 报听、过手限制、死叫判定、轮转、托管及 AI 决策结果和决策参数。
5. 普通鸡、冲锋鸡、责任关系、倍率、杠分、胡分、流局和结算资金转移。
6. 房间准备、开局条件、断线座位归属、权威状态、请求去重、出牌时限和状态提交时机。

规则说明以现有《游戏规则总纲》和对应代码为基线；发现二者矛盾时记录证据，逐项交用户确认，不借优化修正规则。上次用户确认的结算展示规则继续保留：自己的得分鸡显示在自己的得分项，适用于全部其他玩家的项目不写括号，部分玩家才写相对方位。

执行保障：冻结核心规则、AI 和现有规则测试的文件摘要；对固定种子、固定操作序列逐步比较基线与候选的权威状态和结算结果。网络与 UI 混合文件需要逐段审查，不能仅凭“核心文件没改”宣布业务等价。不得为通过测试而改变规则断言、替换期望值或跳过原用例。

## 3. 允许的优化范围

| 编号 | 范围 | 具体要求 | 禁止借机改动 |
| --- | --- | --- | --- |
| PERF-01 | 性能和资源 | 先定位主线程、GPU、分配、加载和音频耗时，再减少重复计算、重复资源加载及无效绘制；资源退出后释放 | 更改 AI 强弱、减少规则检查、跳过合法操作或降低对局信息完整性 |
| NET-01 | 网络传输 | 量化 RTT、抖动、消息大小、重复流量、恢复耗时；按证据改善传输和无效刷新 | 改消息含义、权威归属、优先级、超时规则或向客户端泄露暗牌 |
| MP-01 | 联机体验 | 两端状态一致；进入牌桌、音画显示和连接反馈顺序清楚；重连与前后台切换稳定 | 提前发牌、提前开局、重复提交或重连额外摸牌 |
| VOICE-01 | 语音 | 区分在线 GME 与局域网 PCM；分别测清晰度、延迟、欠载、回声、串音和恢复 | 擅自更换语音服务、默认开启麦克风、绕过鉴权或改变用户音量偏好 |
| UI-01 | 按钮与信息 | 统一安全区和触摸目标；处理操作、整理、返回座位和准备下一局按钮的优先级、位置与高度 | 改按钮的业务条件、操作语义、默认选项或自动帮玩家做决定 |
| ART-01 | 美术 | 保持绿绒、象牙牌、木质边框方向；改善牌桌和牌背区分、光照、材质粗糙度、背景层次和字体对比 | 用过强光效、景深或装饰遮住牌面；未经需求增加全新美术系统 |
| FEEL-01 | 动画与反馈 | 改善出牌、摸牌、碰杠、骰子和翻鸡轨迹、缓动、落桌感、同步与中断清理 | 由动画决定抽到哪张牌、等待动画才变更权威结果、改变操作窗口 |

“包括但不限于”的其他发现先进入问题清单；只有与上述体验直接有关且不触及冻结项的修改才纳入执行。

## 4. UI 与视觉方案

- 信息层级：牌面和合法操作最高，其次是玩家身份、分数与状态，装饰最低。优先减少视觉噪声，再调整材质和灯光。
- 对局布局：保留已确认的视角、四家可读性和行列容量。南北弃牌每行 10 张、最多 3 行；东西每行 8 张、最多 4 行。屏幕下方的牌按真实景深遮挡上方牌底边，不能反向覆盖牌面。
- 碰杠和手牌：四方牌间距保持连续，横牌能表达来源和冲锋状态；在密集和四组碰杠情况下检查，不能只看空桌。自身手牌靠近桌沿，局末按现有流程平铺。
- 状态提示：保留立体三角最新弃牌标记，不恢复牌面金色描边、冲锋鸡说明字样或姓名分数黑底。
- 底部控件：按 2026-11-20 最新要求移除排序、上一种/下一种、恢复按钮，以及排法文字和手牌下金线；保留自动理牌。返回座位和准备下一局继续保留，可覆盖牌体底边，不得覆盖有效牌面。
- 名字分数：四家位置固定，避开手牌、碰杠和安全区，不随当前手牌数量或发牌阶段移动；极长名字不挤走分数和庄家、报听标记。
- 公开牌：各家按独立鸡牌、碰杠首次公开的时间顺序混排，优先在手牌前居中；普通弃牌和他家动作不移动已有公开组。补杠先让位再入位；对家来源明杠的横牌与三张主牌居中，主排按近手边缘对齐。
- 发牌动画：落点与实际本家手牌使用相同变换，开局 4/8/12/13 张均不得在落地重建时跳位；手牌和摸牌底边统一。
- 桌面翻鸡、下一墩堆叠和结算面板同时可见。仅调整展示位置，不改变翻出的是哪张牌及其数组来源。
- 美术先产出相同场景的前后对照图，检查 100% 图片与手机尺寸缩图；清晰度优先于反光、阴影和装饰。

## 5. 性能、网络与声音方案

1. 同一硬件配置建立冷启动、空闲、正常对局、密集碰杠、动画和结算分段基线，记录帧时间分布、进程 CPU、PSS、GPU/绘制、网络和音频事件。
2. 正常性能统计与高频截图分开运行。10 帧/秒截图用于动画审查，其额外负载必须单独记录，不能把截图引起的卡顿当游戏本身的问题。
3. 两端联机先使用专用测试房间和本地服务，再验证线上测试房间；不干扰真实玩家或修改生产配置。
4. 网络按正常、延迟抖动、丢包和断网恢复分别测。公网偶发 500ms 不可凭客户端改动保证消失，要区分客户端排队、服务端耗时和链路耗时。
5. 在线 GME 和局域网 PCM 分开验收。两模拟器互传固定语音并录制接收端声音，验证内容、延迟和中断；不能以“收到包”替代听感与音频证据。
6. 优先复用已有测试、Android Perfetto/系统采样与现有 Godot 监测入口。只在存在明确缺口时增加工具，不为优化引入大型依赖或替换 SDK。

## 6. Skill 查找与使用

已明确使用 `find-skills`：先查看 skills.sh 榜单，再用 `npx skills find` 按 Godot 性能、UI、联机、语音和素材检索，核对来源、安装数、仓库活跃情况与实际内容。搜索热度仅作筛选，不当作质量保证；技能建议不得覆盖本项目规则冻结要求。

| 工作 | 优先使用的现有技能 | 使用边界 |
| --- | --- | --- |
| 需求、界面层级 | `game-design`、`game-ui-ux` | 只分析可读性、操作负担和界面，不重设计玩法 |
| Godot 布局 | `godot-ui-control` | 结合本项目 2280×1280、canvas_items/expand 与真实安全区 |
| 美术和模型 | `create-game-assets`、`godot-3d-prop-integration` | 先复用素材，记录授权、尺寸、导入和材质成本 |
| 动画和反馈 | `game-feel`、`godot-animation` | 只改表现，保持业务状态与操作时机 |
| 联机与恢复 | `godot-multiplayer` | 保留已有传输架构，不能因示例使用 ENet 就替换现有在线服务 |
| 修改与复核 | `ponytail`、`ponytail-review` | 每项修改可追溯到问题，独立审查规则边界 |
| 性能、音频专项 | 经 `find-skills` 验证的候选 | 内容适配后才使用；不匹配 GME/安卓的建议不得照搬 |

检索结果、链接、实际调用和候选取舍登记在验收文档的执行记录中。已有技能足够时不重复安装；新增技能仅限经审查、确实适用的项目。本次已补装并阅读 `performance-optimization` 与 `godot-audio`，后者仅用于播放/混音分析，实时通话继续依据 GME/PCM 实现验证。

## 7. 按难度分配模型

| 难度 | 工作 | 模型分工 | 合入条件 |
| --- | --- | --- | --- |
| 低 | 清点、日志归纳、截图索引、运行既有检查 | `gpt-6-luna` | 输出可追溯证据，不自主修改规则或评判复杂等价性 |
| 中 | 局部 UI、资源配置、测量脚本、明确热点优化 | `gpt-6.1-sol` | 复现、局部差异、对应测试与前后对照 |
| 高 | 跨线程卡顿、联机恢复、语音链路、状态等价和最终风险审查 | `gpt-6-astra`；可用性不足时由主代理承担并明确记录 | 独立复核、规则对比、双端和持续测试；额度不足不降低标准 |

这是任务分配方案，不是所有模型均已成功执行的声明。每个任务记录实际模型、范围和结果；复杂问题不因为快速模型给出结论就直接合入。不同代理使用独立负责文件，不能同时改同一模块。

## 9. 问题处理与变更约束

- 每局结束先校验并记录，再开下一局。同一问题独立出现两次，暂停后续轮次，修复后先重放相关场景，再继续稳定性轮次；失败局不计入通过数。
- P0：规则变化、状态错乱、崩溃、暗牌泄露；P1：阻塞操作、牌面不可读、持续断音或严重卡顿；P2：可使用但不够清楚、轻微抖动或美术不一致。
- 修改按单一问题分批，记录“问题 → 修改文件 → 测试 → 证据”。性能无收益或画质回退的改动撤回，不进行顺手重构。
- 规则疑点、设备限制、模型额度、网络或工具失败必须明示，不用假数据补齐。
