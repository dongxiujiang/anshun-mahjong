# 项目体验优化验收标准

版本：1.0；日期：2026-11-19；状态：验收计划，以下目标不是已测结论。

对应：[项目体验优化需求文档](项目体验优化需求文档.md)。需求编号为所有变更、测试与证据的关联依据。

2026-11-20 新增 [牌桌布局规范](牌桌布局规范.md) L01–L11 作为布局专项的最新验收依据；旧的整理工具栏可见性、身份区跟随手牌要求已被用户明确替代。玩法与计分测试继续冻结。

## 1. 通过判定

- 结论仅使用：通过、失败、受阻、未测、不适用。不适用必须写原因，受阻和未测均不能视为通过。
- RULE-01 必须全部通过；P0、P1 必须清零。P2 必须列明剩余影响，不得隐瞒后宣布“没有问题”。
- 无窗口/无 GPU 测试只能证明逻辑或布局计算，不证明渲染清晰、实际帧率、触摸手感或语音听感。
- 所有性能指标是本轮初始验收目标；先测基线，再确认设备能力。如果目标不可达，提交原因和替代方案，不能在报告里静默放宽门槛。

## 2. 环境与证据要求

每次报告必须带：源码提交和未提交差异摘要、APK/PCK SHA-256、安装包标识、Godot 与原生插件版本、安卓版本、模拟器版本、CPU/内存/GPU 配额、渲染方式、屏幕尺寸/密度/安全区、刷新率、音频设备、服务端版本及网络条件。

证据统一存放 `build/quality-optimization-evidence/<阶段>/<运行编号>/`。保留原始日志、采样文件、截图、录音、测量方法和汇总，避免只保存平均值或拼图。

## 3. RULE-01：规则与业务等价，零容忍

| 检查 | 操作 | 必须满足 |
| --- | --- | --- |
| 冻结文件 | 对核心规则、AI、规则测试和规则总纲做 SHA-256 比对 | 内容与继承基线一致；新增/删除文件也要发现 |
| UI/联机混合代码 | 复核所有差异与调用方 | 不改变权威状态、合法动作、定时条件、消息含义和暗牌可见范围 |
| 固定回放 | 至少 20 个固定种子，保存并重放相同的操作序列；特殊场景单独补 fixture | 每一步牌墙身份/剩余量、手牌/碰杠/弃牌归属、轮次、合法操作和权威状态摘要一致，最终分数与逐笔账本一致 |
| 边界回归 | 四方分别覆盖报听、碰、三类杠、抢杠、补牌、胡、流局、耗尽不翻鸡、死叫和鸡分 | 既有断言全过；覆盖表中每项有用例和结果 |
| 动画隔离 | 正常、快速连播、前后台中断和重连后比较 | 牌面及落点源自同一权威状态，动画不增减牌、不改结算、不阻断合法动作 |
| 联机一致 | 相同操作流对比基线/候选和双方视角 | 同一修订号的允许公开状态一致，重复/过期操作不会额外生效 |

仅做文件摘要不能单独判定规则不变；仅最终分数一致也不能单独判定取牌过程一致。

## 4. PERF-01：流畅度、CPU 与内存

在目标设备可提供 60Hz 的正常配置下执行；模拟器配额固定，宿主机负载单独记录。60 秒稳定片段至少重复 3 次，报告中位结果及最差运行。

| 指标 | 初始通过目标 | 测法/限制 |
| --- | --- | --- |
| 稳态帧率 | 平均 ≥55 FPS；帧时间 p95 ≤20ms、p99 ≤33.3ms | 运行期帧时间结合 Perfetto；启动、加载、重连单列，不删掉慢帧 |
| 明显停顿 | 正常对局无游戏造成的 >100ms 帧；>50ms 比例 <0.1% | 每个超标事件对应时间线、调用和同刻系统负载；环境故障要留证 |
| CPU | 同配置稳态平均不高于基线 5%；针对已确认 CPU 热点争取下降 ≥15% | 记录占满单核心等于 100% 的口径；低 CPU 不代表 GPU 或主线程无阻塞 |
| 内存 | 同场景峰值 PSS 不高于基线 5%；预热后的同一局末场景应进入平台期，增长 20MB 触发调查 | 每秒采样，报告增长斜率和噪声；区分资源缓存与泄漏，退出进程后无残留游戏进程 |
| 启动/加载 | 冷启动至可操作不回退超过 5% | 启动前开始采集，每组 3 次报告逐次值、中位数和最大值；p95 仅在扩充样本并注明数量后报告；首局资源加载单列 |
| 资源开销 | 不增大固定场景 draw calls/三角面数/显存，除非图像改善明确且仍满足帧预算 | 同镜头、同牌数比较，不能隐藏牌或降低信息完整性换取性能 |

帧率采样使用帧时间，不以每秒截图数量推断帧率。模拟器系统服务崩溃的运行标为无效并重测，但保留故障记录；应用自身崩溃不得作废掩盖。

## 5. NET-01 / MP-01：网络与联机

| 场景 | 注入条件 | 必须满足 |
| --- | --- | --- |
| 正常受控链路 | 基础 RTT ≤40ms，丢包 <0.1% | 端到端操作到确认 p95 ≤150ms；双方状态一致；无重复发牌/出牌和无效高频消息 |
| 一般弱网 | 额外 RTT 100ms、抖动 ±30ms、丢包 1% | 不错局、已由服务端确认的合法动作不丢失；未确认、过期及超时请求按基线处理并反馈；延迟结果含注入条件 |
| 严重弱网 | 额外 RTT 300ms、抖动 ±100ms、丢包 5% | 无崩溃、无分歧、无无限队列；请求过期处理和权限保持基线语义 |
| 断网恢复 | 断网 5 秒和 30 秒，各端分别测试 | 5 秒内反馈连接状态；会话仍有效时目标为恢复联网后 5 秒内可操作，会话已过期时准确反馈；两项分别判定，业务超时规则保持不变 |
| 前后台 | 每端在摸打、响应和结算时分别后台 10 秒/60 秒 | 回到前台后正确恢复当前局；无重复音效、残留动画、串房语音或旧按钮 |
| 准备与开局 | 仅一人准备、全部准备、退出重进和下一局 | 与基线开局条件一致；不提前播放骰子；画面与音效属于同一局事件 |
| 重复/乱序 | 重放重复请求和旧版本状态 | 额外操作不生效，修订号和去重语义不变，不能收到其他玩家暗牌 |

记录 client→server→client 的分段时间、服务端处理时间、RTT、抖动、丢包、重传、消息数和字节数。公网 500ms 尖峰必须归因；不能在未控制链路时承诺任意网络都低延迟。

## 6. VOICE-01：语音清晰度与稳定性

在线 GME 和局域网 PCM 分开，双模拟器双向各测，再在两台真实安卓设备上确认声学表现。麦克风默认开关、按座位收听和音量偏好保持原行为。

1. 使用固定中文语料，包含麻将术语、数字、轻声和连续说话；保留参考音频与接收端实录，测量前对齐采样率、时钟和音量，避免宿主机回环造成假串音。
2. 正常链路的端到端语音延迟 p95 ≤300ms，接收录音无 ≥200ms 的非原始静音中断；连续 10 分钟没有音频输出欠载或不断增长的队列。SDK 不提供欠载计数时标记“不可直接观测”，用接收录音连续性补充，不能仅凭无错误日志判通过。
3. 至少 50 条固定语料双向测试，人工盲听的预先标定关键词正确率 ≥95%（正确关键词数/参考关键词总数，附逐词结果），无明显削波、金属音、爆音。自动识别可辅助，不代替听感；可用时附 STOI 等对齐后的指标，但不能用不适配的评分制造“通过”。
4. 噪声、双讲和扬声器回声在真机单独验证；模拟器只证明数字链路，不能证明降噪和回声消除效果。
5. 弱网下记录中断和恢复；3 秒内反馈连接状态，会话有效时网络恢复后 3 秒内恢复双向语音为目标，分别报告反馈和实际恢复耗时；不串房、不听见已离开的座位、不把静音自动解除。
6. 权限拒绝、麦克风被其他应用占用、音频焦点切换、后台返回、进退房各 10 次，无崩溃、无资源残留。

仅双模拟器合格时，结论写“数字链路通过，真机声学与人工听感待验”，不能宣布真人双端语音全部通过。

## 7. UI-01 / ART-01：布局与美术

测试尺寸：1280×720、1600×1000、1920×1080、2400×1080；另覆盖 16:9/20:9 和至少一组刘海/手势安全区。记录密度，触摸目标按实际 dp 换算，不能把设计像素当 dp。

| 检查 | 覆盖 | 通过标准 |
| --- | --- | --- |
| 四家可读性 | 4 个观察座位 × 4 个玩家；满手牌、摸牌、0/2/4 组碰杠 | 所有公开牌、来源横牌、鸡牌、身份分数和必要状态可辨认 |
| 弃牌 | 南北第 10/11/20/21/30 张，东西第 8/9/16/17/24/25/32 张 | 行列与需求一致，行内连续、行距紧凑、前后遮挡正确，无组间穿插 |
| 碰杠间距 | 每个拥有者 × 3 个来源 × 明杠/碰/补杠，另测暗杠 | 四方贴近规则一致；横牌位置清楚；不穿入相邻组和手牌牌面 |
| 庄家/报听 | 4 庄家 × 16 种报听状态组合 | 64 组均与状态一致，位置不漂移，不被名字或控件遮住 |
| 翻鸡和结算 | 有支撑/底层翻出、牌墙将尽、完整/不完整下一墩、无牌 | 牌源保持基线；桌上翻鸡可见，不悬空、无多余残墙；结算不挡关键信息 |
| 按钮 | 常态、响应、结算、重连、不同手牌长度与 4 组碰杠 | 关键按钮触摸区域 ≥48dp，间隔 ≥8dp；在安全区内，无重叠抢点击，无牌面遮挡 |
| 触摸验证 | 每种主要按钮/牌中心和边缘各 20 次 | 本次样本全部正确触发，无误出牌、无重复提交、无点不到的底部按钮；不从有限样本推断总体零故障 |
| 文本和配色 | 最长名字、正负大分数、禁用态、手机尺寸缩图 | 正文对比目标 ≥4.5:1；牌背与桌布区分清楚；不靠颜色单独传递状态 |
| 图像质量 | 同场景前后 100% 截图和缩图 | 牌面清晰，无锯齿闪烁、过曝、阴影脏块；不用模糊/景深掩盖牌面 |
| 既有要求 | 正常对局与结算 | 无牌面金色描边；无冲锋鸡文字标记；名字分数无黑底；得分项方位符合既有规则 |

若 48dp 与牌面不遮挡在目标横屏上冲突，先提交具体尺寸与布局对照解决，不悄悄缩小触摸目标或手牌。

## 8. FEEL-01：动画与声音同步

- 正常、最低/最高已有动画速度分别验证摸牌、出牌、碰、三类杠、补牌、骰子、翻鸡、结算平铺。
- 10 帧/秒截图配合原始高帧率录屏或逐帧渲染。10 帧/秒不能单独证明没有一帧闪烁或音画延迟。
- 起点、终点和牌墙消失位置与权威牌 ID 一一对应；无瞬移、重复牌、悬空、穿桌、落地后漂移和跨局残留。
- 同一事件的落桌声音和可见接触目标偏差 ≤80ms；第一帧响应反馈目标 ≤100ms；动画不得改变已有合法操作时机。
- 快速状态更新、断线重连和前后台中断后动画收束到最新状态；同一事件音效仅播放一次。

## 9. 综合运行协议

1. 从游戏未启动时开始监测。冷启动 → 5 局真实操作流程 → 关闭 → 确认退出；重复两轮。每局先审核、记录，再开下一局。
2. 定向用例通过后再进行 20 局稳定性运行。全部后台；开启和关闭截图的运行分别统计，正常运行不抢占用户前台。
3. 每局记录种子/房间、各阶段时间、帧数据、CPU、PSS、网络、声音、错误、结算与截图索引。用固定种子覆盖极端场景，不能把随机 20 局当作穷举。
4. 相同问题两次复现即暂停轮次，修复后先校验相关用例和规则等价，再重新开始受影响的通过计数。未经修复和复测的问题不能被后面成功局抵消。
5. 按改变范围运行局部测试；最终候选再运行全套规则、布局、联机和专项验收。修复之后的新版本结果不能沿用修复之前的合格报告。
