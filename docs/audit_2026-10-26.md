# 安顺麻将代码 / 规则 / 测试审计

日期：2026-10-26  
范围：`scripts/`、`server/`、`tests/`、发布脚本、现行规则文档  
版本：本地 1.5.25，线上 1.5.25

## 一、总体结论

核心对局、发牌、计分、UI 布局和大多数回归测试是稳定的，`run_suites.py` 当前 71/71 通过。

但发布链路和联机测试功能仍有高风险问题，主要集中在：

1. 热补丁基线被手工修改，1.5.25 热补丁可信度不足；
2. 客户端、GitHub 标签、线上服务器镜像没有强绑定；
3. 联机开局速度存在客户端动画与 lobby 的时序窗口；
4. 测试牌型功能可用，但属于调试功能，服务端没有 debug 限制；
5. 杀报结算刚改，规则文档未同步；
6. 部分测试是临时调试脚本，没有纳入正式回归。

## 二、高优先级问题

### P0-1 热补丁基线被手工归一化，1.5.25 热补丁需要重新验证

证据：

- `tools/update/prepare_hot_update.py` 中 `run_godot()` 会过滤 `resources still in use at exit` 和 `ObjectDB ... leaked`，可能把真实导出错误一并吞掉；
- 1.5.25 打包时，`baseline.json` 的 `boot/classes/native/settings/export` 被手工替换为当前快照值，而不是使用 1.5.24 安装包真实基线；
- 最终生成了 79,176 字节的 1.5.25 PCK 并已上线。

风险：

- 1.5.24 客户端下载补丁后可能出现加载失败、闪退、类校验失败；
- 当前没有在真实 1.5.24 安装包上验证过该补丁。

建议：

- 用 1.5.24 原始 APK/PCK 重建基线；
- 在 1.5.24 真机或等价环境安装 1.5.25 补丁，验证启动、开局、结算；
- 在验证前，优先使用完整 APK，不要依赖热补丁。

### P0-2 三方版本没有强绑定

当前同时存在：

- 本地代码版本 `1.5.25`；
- GitHub `V1.5.25` 标签；
- 线上服务器镜像 `sha-53e6d67`，基于更早的 1.5.24 代码；
- 自建 manifest 指向 1.5.25 APK/PCK。

风险：

- 服务器和客户端规则可能不一致；
- 修了客户端但没有部署服务器，联机仍然走旧逻辑；
- 回滚时无法确定应该回滚到哪个镜像/哪个 APK。

建议：

- 发布记录中固定记录 `Git commit + tag + APK sha256 + server image digest + manifest version`；
- 部署服务器必须由同一个 commit 的镜像完成；
- 增加发布后自动校验接口，比对版本与 commit。

### P1-1 联机开局动画可能先于 lobby 速度到达

证据：

- `TableAnimationController.gd` 在收到 `dice` 事件时才读取 `net.lobby.opening_speed`；
- 远端测试中，客户端先拿到 game state，`lobby` 还是空的，随后才收到 `owner/opening_speed`；
- 如果此时已经开始播放骰子/发牌，客户端会退回 `standard`，而服务器可能按 `fast` 等待。

后果：

- 房主设置 fast 时，客户端动画仍按 normal 播放；
- 服务器提前进入摸牌，客户端动画未结束；
- 用户观感就是“设置快没生效”或“理牌后还等”。

建议：

- 把 `opening_speed` 放进房间创建响应和第一份 state 快照，而不是只依赖后续 lobby；
- 或在客户端收到第一份 `opening_speed` 前延迟播放开局动画。

### P1-2 测试牌型覆盖会制造超过 4 张同牌

证据：

- `RoundState._initial_deal()` 先完成正常 53 张发牌，再把指定座位手牌整体替换为 `test_hand`；
- 原随机牌已经从牌墙抽出，测试牌仍留在牌墙/其他玩家手里；
- 牌张总数仍是 108，但同一张牌可能超过 4 张。

后果：

- 测试牌型下牌墙统计和真实牌理不一致；
- 可能影响碰/杠/自摸概率、AI 估算和回放。

建议：

- 测试模式用独立牌墙构建：先移除测试手牌，再洗牌、发牌；
- 或在文档中明确“测试牌型不是合法牌墙，只用于 UI/流程测试”。

### P1-3 测试牌型服务端没有调试开关

证据：

- 正式包通过 `GameConfig.debug_enabled` 隐藏按钮和投票卡片；
- 服务端 `_start_test_vote` 不检查 debug 标志；
- 旧 RPC `request_test_pattern` 仍然保留。

后果：

- 修改过的客户端或旧客户端仍可向正式服务器发起测试牌型；
- 不显示 UI 的玩家可能被强制进入测试局。

建议：

- 房间创建时带 `test_mode` 标志，仅 debug 房允许提案；
- 删除或限制旧 RPC；
- 服务端对提案来源做 debug 校验。

### P1-4 测试牌型投票没有提案 ID / 并发保护

证据：

- `_test_vote` 是单个字典；
- `_start_test_vote` 新提案会直接覆盖旧提案；
- 客户端只按 `test_vote` 内容投票，没有 `proposal_id`。

后果：

- 两个人同时发起时，前一个提案会被静默覆盖；
- 旧提案的同意票可能被算到新提案；
- 玩家看到的投票卡片可能和服务器实际提案不一致。

建议：

- 增加 `proposal_id`、创建时间和过期时间；
- 有 active proposal 时拒绝新提案；
- 投票必须带 `proposal_id`。

### P1-5 杀报新规则未写入规则文档

证据：

- `WinScoring.gd` 当前规则：自摸者未报听、付款者已报听时，付款者付完整牌型分 + 杀报24 + 鸡分/杠分，不再另加自摸4；
- `docs/rules_update_validation.md` 仍写“自摸由另外三家各付完整值”“报听和杀报按各自付款关系另计”，没有新例外。

后果：

- 后续开发/测试可能按旧文档改回错误逻辑；
- 玩家与客服对账时口径不一致。

建议：

- 在规则文档明确“报听付款者例外”；
- 补充 0 牌型、普通牌型、大牌三种示例；
- 把 `rules_update_validation.md` 作为唯一规则源，测试引用它。

## 三、中优先级问题

### P2-1 旧 RPC / 重复同步路径

- `request_test_pattern()` 仍存在，但客户端已改走 `lobby_action test_propose`；
- `request_opening_speed()` 仍存在，但客户端已改走 `lobby_action opening_speed`；
- `GameTable._opening_speed_synced` 与 `NetGameNode._report_opening_speed()` 两套同步逻辑并存。

风险：未来维护者改一处漏一处。

### P2-2 测试牌型手牌与发牌动画不一致

正常发牌动画先展示随机牌，随后 state 覆盖为测试手牌；可能出现一帧或一段动画的“换牌”观感。

### P2-3 debug 开关切换后按钮不立即出现

`TableLayout` 只在布局时根据 `GameConfig.debug_enabled` 决定测试按钮显隐；在牌桌设置中刚打开 debug 时，按钮不会立刻重排，需要退出重进。

### P2-4 AI 教学重复推理

`TableActions._build_turn_options()` 调一次 `AI_TEACH.recommend()`，随后 `GameTable._refresh_ai_assist()` 又调一次。移动端可能产生一次额外 AI 计算和帧抖动。

### P2-5 AI 只推荐一个牌种

`AiTeaching.recommend()` 返回单个 `tile`；相同牌的多张副本会全部高亮，但不同牌种的等价最佳弃牌不会同时高亮。

### P2-6 临时联机测试脚本未纳入正式回归

当前存在：

- `tests/test_pattern_net_host.gd`
- `tests/test_pattern_net_client.gd`
- `tests/test_pattern_remote.gd`

它们是手工/环境依赖脚本，未进入 `run_all.gd`，但留在源码树中，容易误用。

### P2-7 结算明细金额与实际付款可能不完全一致

`WinScoring` 的 `items[winner]` 仍记录完整牌型分，而报听付款者可能只付牌型分（无额外4）或只付24；结算明细的 own_amount 与逐家转账是两套口径，需要确认 UI 是否会把它们混加。

## 四、规则不明确 / 冲突清单

1. **“大牌”定义**
   - 是牌型分 > 0？
   - 还是仅清一色/七对/大对子等特定牌型？
   - 当前代码按“有牌型分”处理，但没有统一定义。

2. **多个报听付款者被自摸**
   - 每个报听者都付 24 杀报吗？
   - 每个报听者都按牌型分付款吗？
   - 当前代码对每个 ready payer 分别处理，没有专门测试覆盖多 ready payer。

3. **多个赢家 + 杀报**
   - 一个报听者同时被多个未报听赢家自摸，要付几份24？
   - 当前按每个 winner 单独结算，可能重复。

4. **报听者自己有大牌自摸**
   - 报听自摸有牌型时，是否仍按“牌型分+报听20”？
   - 当前 `player.ready` 分支仍加 20/24，需要规则确认。

5. **干扣/大干扣与杀报**
   - 未报听赢家无牌型、无鸡时是干扣14；
   - 若付款者报听，是付干扣+杀报，还是只付杀报24？
   - 当前代码：有 pattern 付款者付 pattern，无 pattern 付款者付0+杀报；干扣同样被跳过。

6. **测试牌型是否允许改变牌墙合法性**
   - 当前测试牌型可能产生同牌超过 4 张；
   - 需要明确“仅 UI 测试”还是“必须合法牌墙”。

7. **正式包是否允许 debug 测试功能**
   - 当前正式包隐藏入口，但服务端未禁用；
   - 需要明确是“客户端隐藏”还是“服务器拒绝”。

## 五、测试覆盖缺口

现有 71 个套件覆盖较好，但缺：

- 真实远端房间的完整投票链路自动化（当前只有手工脚本）；
- 双真人/多真人全票同意与拒绝；
- 多 ready payer 的杀报结算；
- 报听者拿大牌自摸；
- 开局速度 first-round lobby 时序；
- 测试牌型牌张合法性；
- 1.5.24 → 1.5.25 热补丁真机升级；
- 正式包测试按钮隐藏；
- debug 开关即时切换。

## 六、建议修复顺序

1. 重做 1.5.25 热补丁基线并在 1.5.24 真机验证；
2. 把 opening_speed 放进首份 state/创建响应，消除动画时序；
3. 服务端加 test_mode/debug 限制；
4. 投票加 proposal_id/超时/拒绝并发；
5. 更新规则文档并把杀报新规则写清楚；
6. 清理旧 RPC 与临时联机测试脚本；
7. 补多 ready payer、多赢家、热补丁升级测试；
8. 固化发布记录：commit/tag/APK hash/镜像 digest/manifest 一体。
