# 服务端与官网前后端说明

在线服务采用**一体化轻量架构**：同一个 Python 3 服务进程（`remake/server/room_directory.py`）同时承担协议 4 房间目录、权威无头牌桌拉起、牌谱重演校验、版本分发 API 以及官方门户前端静态承载，确保部署简单且与客户端共用同一套规则引擎。

---

## 一、组件职责

- **`remake/server/room_directory.py`**：多线程 HTTP 服务（并发信号量保护、速率限制、可信反代 IP 解析），每创建一个在线房间即拉起一个独立无头 Godot 进程（`res://src/network/RoomServer.gd`），通过 UDP ENet（默认 `7600–7631/udp`）与玩家直连。
- **`remake/server/portal_api.py`**：管理可下载版本清单（`releases.json` + 自动扫描 APK）与 `.pck` 热补丁清单（`hotpatches.json` + `GDPC` 魔数与 SHA-256 fail-closed 校验）、缓存 SHA-256 哈希、SQLite 持久化下载次数统计，以及严格路径隔离的静态前端分发。
- **`remake/server/round_records.py`**：SQLite 牌谱归档，提交时调用 `res://src/network/VerifyRecord.gd` 用真实规则引擎重演校验，防伪造、防覆盖，并支持在线权威 HMAC-SHA256 验签。
- **`remake/server/gme_auth.py`**：为已验权的在线房间成员签发实时语音鉴权令牌。
- **`remake/web/`**：新中式官方门户网站（`index.html`、`styles.css`、`app.js`、`favicon.svg`、`screenshots/*.jpg`），零外部 CDN 依赖，内网与公网均可毫秒级首屏打开。

## 二、后端 REST API 接口清单

所有 JSON 响应均包含 `"protocol": 4, "variant": "anshun_zhuoji"` 协议头。

| 方法与路径 | 鉴权 | 说明 |
| --- | --- | --- |
| `GET /` | 公开 | 东秀麻将官方门户首页（展示游戏特性、下载客户端、在线茶馆查房/建房与接口联调台） |
| `GET /v1/status` | 公开 | 返回服务健康状态、运行时长、活跃房间数/上限、当前在桌人数、牌谱汇总数、总下载量及最新版本信息 |
| `GET /v1/rooms` | 公开 | 返回所有存活在线房间及四座公开状态 |
| `GET /v1/rooms/{4-8位房号}` | 公开 | 按房间号精准查询单个房间状态 |
| `POST /v1/rooms` | 限流（3次/分/IP） | 创建在线房间并启动无头 Godot 牌桌进程，返回房号、ENet 主机/端口与 `owner_token` |
| `GET /v1/releases` | 公开 | 返回可下载客户端版本列表（含版本号、大小、SHA-256、更新日志、下载次数） |
| `GET /v1/releases/latest` | 公开 | 返回最新推荐下载版本元数据 |
| `GET/HEAD /v1/updates/manifest` | 公开 | 返回双层在线更新清单（`schema: 1`、`latest_release`、分平台 `packages` 以及经过 `GDPC` 魔数与 SHA-256 校验的 `.pck` `hotpatches` 列表） |
| `GET/HEAD /v1/downloads/{文件名}` | 公开 | 记录下载计数并分发安装包/热补丁（`.apk`/`.exe`/`.zip`/`.pck`）；支持生产 Nginx 静态目录 302 极速分流，或独立运行时流式 `Range` 断点续传 |
| `GET /v1/gme-auth` | `X-Room-Token` | 在线语音令牌签发（防重放 nonce 校验） |
| `POST /v1/records` | 在线模式需 HMAC | 上传单局牌谱，经无头引擎 100% 规则重演通过后入库 |
| `GET /v1/records` / `GET /v1/records/{id}` | `Authorization: Bearer` | 管理员诊断读取归档牌谱元数据与完整回放（需配置 `RECORDS_API_KEY`） |

## 三、部署与运维

### 生产环境拓扑（`https://mj.dongxiu.fun`）

- **Nginx（宿主机 443 TLS）**：
  - `location /v1/` → 反向代理至重制服务容器（HTTPS `8096`）
  - `location /updates/` → 直接由 Nginx `sendfile` 高速提供 `/var/www/mahjong/updates/` 下的 APK 安装包
  - `location = /` 及官网静态资源（`/styles.css`、`/app.js`、`/favicon.svg`、`/screenshots/`）→ 反向代理至重制服务容器提供官方门户页面
- **Docker 镜像（`Dockerfile`）**：打包 `remake/game`、`remake/server`、`remake/web` 与 Godot 4.7.2 Linux 无头运行时，以非 root 用户 `mahjong` 启动。
- **关键环境变量**：
  - `PUBLIC_HOST`：下发给客户端连接的公网域名/IP（如 `mj.dongxiu.fun`）
  - `MAX_ROOMS` / `FIRST_PORT`：并发房间数与 UDP 端口起始值（如 `16` / `7600`）
  - `DONGXIU_DOWNLOADS_DIR`：服务端安装包目录（生产挂载 `/var/www/mahjong/updates` 只读）
  - `DONGXIU_DOWNLOAD_REDIRECT_PREFIX`：生产设为 `/updates/`，统计计数后交由 Nginx 高速分发大文件
  - `RECORDS_API_KEY`（可选）：管理员读取私人牌谱的 Bearer 密钥
  - `GME_APP_ID` / `GME_APP_KEY`（可选）：在线语音服务凭据

## 四、局域网失联与房主交接调研（2026-11-28，历史方案）

**后续决定已取代本方案：用户要求直接移除局域网模式，仅保留单机与在线。当前工作区已删除局域网搜索、手机开房和备用接管，以下内容仅保留为问题分析记录，不代表仍计划实现自动交接。原局域网专用测试已退役，备份与原始证据保留在 `build/solo-online-startup-20261128/retired-lan/`。** 在线模式继续使用独立权威房间，当前单机/在线启动与测试说明见《客户端架构与 UI》《发布与测试记录》最新条目。

本节按用户“先分析，再查找 GitHub 成熟游戏设计”的要求记录调查与建议，不代表下列方案已经实现或通过验收。麻将规则、固定牌墙数组、摸补牌、胡牌与鸡分计算不在本次改动范围。

### 已复现的问题

OPPO 上的原服务器仍然存活，加入者断线后却恢复备份并在自己设备上另起服务器。两台设备因此各自推进牌局，即使房号、房间实例号、局数、提示序号完全相同，也不能证明连接同一张桌。加入者连到自己后显示的低延迟更不能计作重连成功。

当前 `GameClient.gd` 的恢复流程先尝试原地址；连接失败后，`_on_recovery_rooms()` 仍能调用 `_promote_from_standby()`。局域网发现不到广播、原地址超时以及“持有备份”，都不能证明旧服务器已停止。设备实测已两次复现错误接管；新增 `tests/test_lan_network_partition.gd` 使用真实 ENet 与 UDP 断包转发，8 项检查中 2 项失败，分别是“返回存活原服务器”和“不产生第二服务器”。这是待修复回归，不能作为通过记录。

### 成熟开源游戏的实际做法

调查直接阅读下列 GitHub 固定提交的源码，避免把教学样例、第三方介绍或“房主”一词的不同含义当成结论。

| 游戏 | 源码中能确认的行为 | 对本项目的启示 |
| --- | --- | --- |
| The Battle for Wesnoth，回合制策略游戏 | `wesnothd` 的 `remove_player()` 在已开始且仍有玩家的游戏中处理房主离开，选择剩余玩家并由服务器发送 `host_transfer`；未开始时房主离开会结束房间。 | 新房主由仍在运行的服务器指定；这段逻辑不是失联客户端自行启动另一台服务器。 |
| OpenRA，即时战略游戏 | `DropClient()` 在独立服务器、等待玩家阶段可另选管理员；玩家本机托管的非独立服务器失去管理员时调用 `Shutdown()`。 | 房间管理员的转移与实际服务器的迁移是两件事。不能看到“可换房主”就照搬成断线自建服务器。 |
| Mindustry，建造与战斗游戏 | 所检查的 `NetClient` 断线处理重置连接/游戏并提示错误；接到完整 `WorldStream`、加载世界后才完成连接；另检测长时间收不到 UDP 状态快照。 | 连接成功、收到当前游戏状态、游戏状态仍在更新，需要分别确认。所查断线路径没有自动变成服务器。 |

### 适合本项目的建议

用麻将桌比喻：房主是组织牌局的人；实际服务器是记住整副牌和裁定每一步的裁判。组织者可以换人，裁判不能因为某个人暂时听不到，就凭空变成两位。

1. **先修复同桌恢复。** 普通加入者暂离、断网、弱网或单向断包，只能寻找并连接原权威；本地保留最后画面并清楚显示重连状态，禁止从旧快照继续提交动作或开下一局。连上后验证房间及服务器身份，接收当前局完整且按座位过滤的快照，确认应用完成再恢复输入。跨局回来直接同步当前阶段，迟到快照和旧动画/音效不能把人带回上一局。
2. **分开房间管理与实际权威。** 房间管理员可以由同一权威指定替换。承载服务器的手机只返回大厅、仍在运行服务器时，不必另建服务器；整应用退出、被系统杀死、手机关机与单纯离开座位必须区分。当前服务器虽然是独立根节点，仍处于同一个安卓进程，`PROCESS_MODE_ALWAYS` 不能保证锁屏/后台后不被系统暂停。
3. **正常退出再做受控交接。** 如果需要迁走实际服务器，由旧服务器暂停接受新动作、固定已提交状态、选定接收者、交付检查点并确认接收者就绪；旧服务器持久记录退役并停止裁决，再签发唯一交接凭据，新服务器接续。网络中断导致交接不明时保持等待，不能两边自行继续；旧服务器恢复后也须遵守退役状态。世代号必须由这一流程或统一仲裁者授予，不能客户端各自加一。
4. **突然失联不能保证无条件自动接管。** 在只有两台设备且纯离线时，某台手机无法区分“对方关机”和“自己断网”。若两边都允许凭超时续局，就仍可能分成两桌。建议默认等待原服务器或结束当前连接；如果提供备份重开，应明确新房间/恢复分支身份，不能伪装成原桌无缝续局。手动点“确认”本身也不是旧服务器已退出的证据。
5. **在线模式继续使用统一服务器。** 手机掉线只恢复该房间和原座位，不在手机上接管权威。如果将来坚持要求“局域网房主突然关机也自动续局”，需另立需求，引入在线仲裁与可撤销授权，或实现有多数设备同意才能推进的离线一致性协议。后者在两台真人设备时不能提供单台继续能力，AI 座位不算额外设备；本次不为四人麻将直接引入整套共识系统。

上述第 4、5 点是结合本项目设备数量作出的设计分析，不是声称三款参考游戏都使用同一种算法。分区时仍可保持一致、但需要多数成员通信才能继续的通用依据见 [Raft 原论文第 2 节及选举规则](https://raft.github.io/raft.pdf)。

联网报文若增加权威身份/世代/交接凭据，需要升级并检查协议兼容性；旧版仍会自行接管，不能只发布一台新客户端就宣称混合版本安全。普通客户端快照和日志不得包含其他座位暗手或未摸牌墙；备用权威数据的权限边界需单独核对。

### 建议验收标准（未执行）

| 场景 | 必须看到的结果 |
| --- | --- |
| 加入者切桌面、微信或锁屏，跨下一局后回来 | 先在另一台设备确认暂离；回来进入同一存活服务器的当前局，同座位、正确手牌与操作权限，不播上一局骰子/翻鸡。 |
| 短断线、长断线、单向断包、双向隔离；恢复广播失败但直连可达 | 先确认另一台显示离线再恢复；原权威存活时无第二权威，恢复到原权威。正常局域网恢复可达后，建议 5 秒内取得当前快照并恢复输入；弱网单独记录，不混入该时间预算。 |
| 房间管理员离座；承载服务器的应用仍在运行 | 管理员变化不重建规则状态、不重发牌、不产生第二桌。 |
| 实际服务器正常交接，交接中途断网，旧手机随后返回 | 任一时刻只有一个被授权接受新动作的服务器；交接不确定时停止推进，不能回退已确认操作或重复结算。 |
| 原服务器被强停、关机或系统杀死 | 遵守最终选定的失联策略，不能以客户端自行建同号房间冒充重连通过。 |
| 弱网 128 kbps / 每方向 300±80 ms / 2% 丢包及更差链路 | 不分桌、不重复动作；分别记录 RTT、状态停更时间、备份 ACK 等待、恢复耗时；UI 继续响应，不能只看延迟数字。 |
| 迟到上一局报文、重复操作、旧权威报文、混合版本 | 拒绝过期/不兼容输入；不回退局数或牌墙位置，不重复摸牌/计分。 |

验证应同时记录服务器身份与世代、实际远端、局号、已应用状态序号、公共牌局摘要，以及服务器对每个座位私有快照的核对结果。各座位私有视图不同，不能直接比较整份客户端快照哈希；相同房号、局号或连接成功提示都不足以单独验收。需覆盖 OPPO 真机和专用模拟器，双档画质复测，待最终方案实现后再做连续对局与发布验收。
